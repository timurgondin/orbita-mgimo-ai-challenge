# Безопасность «Орбиты»

> Как устроены вход, хранение паролей и разграничение доступа. Документ — ТЗ для агентов и основа раздела «Безопасность» в отчёте для жюри.

## Требования ТЗ хакатона

- Студент видит только свои данные — чужой профиль или заявку не открыть, даже подставив другой адрес.
- Пароли не хранятся в открытом виде.
- Ключи и пароли от сервисов не лежат в коде и в браузере пользователя.

## Пароли: Argon2id + соль + перец

**Алгоритм — Argon2id.** Победитель Password Hashing Competition, рекомендован OWASP и RFC 9106. Вариант «id» сочетает защиту от атак по сторонним каналам (Argon2i) и от перебора на GPU/ASIC (Argon2d). Алгоритм «дорогой по памяти»: каждая проверка требует десятки мегабайт RAM, поэтому массовый перебор на видеокартах становится экономически бессмысленным.

**Параметры** (минимум OWASP — m=19 MiB, t=2, p=1; мы берём с запасом):

| Параметр | Значение | Смысл |
|---|---|---|
| `memoryCost` | 65 536 KiB (64 MiB) | память на одно вычисление |
| `timeCost` | 4 | число проходов |
| `parallelism` | 1 | потоки (сервер на 2 ядрах) |
| `outputLen` | 32 байта | длина хеша |
| соль | 16 случайных байт, своя у каждого пароля | генерирует библиотека через CSPRNG |

Цель — 100–300 мс на одну проверку на нашем сервере. Параметры вынесены в конфиг; при логине, если хеш создан со старыми параметрами, пароль прозрачно перехешируется (`needsRehash`).

**Соль** хранится внутри строки хеша (формат PHC: `$argon2id$v=19$m=65536,t=4,p=1$<соль>$<хеш>`). Одинаковые пароли у разных людей дают разные хеши, радужные таблицы бесполезны.

**Перец (pepper)** — секретный ключ 32 байта, который **не хранится в базе**, только в переменной окружения `AUTH_PEPPER` на сервере. Передаётся в Argon2id как параметр `secret` (встроенное keyed hashing, без самодельных HMAC-обёрток). Если утечёт только база — хеши невозможно перебирать без перца. У пользователя хранится `pepperVersion`, чтобы перец можно было сменить.

**Библиотека:** `@node-rs/argon2` (нативная Rust-реализация с готовыми сборками, поддерживает `secret`). Сравнение хешей — константное по времени внутри библиотеки.

## Вход

- Одинаковая ошибка «Неверный логин или пароль» для несуществующего логина и неверного пароля.
- Защита от перечисления логинов по времени ответа: если пользователь не найден, всё равно выполняется проверка против заранее вычисленного фиктивного хеша.
- **Ограничение попыток:** не больше 5 неудачных попыток на пару «логин + IP» за 15 минут, затем временная блокировка с понятным сообщением. Счётчик хранится в БД. Общий лимит на логин сознательно не делаем: им бот мог бы заблокировать любой чужой аккаунт. IP берётся из заголовка, который ставит наш reverse proxy (`X-Real-IP` или правое значение `X-Forwarded-For`), — подставить свой IP клиент не может.
- Логин нормализуется (trim, lower-case), длина полей ограничена (пароль ≤ 256 символов — защита от DoS длинной строкой).

## Сессии

- После входа сервер создаёт **непрозрачный случайный токен** (32 байта из CSPRNG). В браузер он уходит в cookie, в базе хранится только его **SHA-256** — утечка базы не даёт угнать сессии.
- Cookie: `HttpOnly` (недоступна JavaScript), `Secure` в продакшене, `SameSite=Lax`, `Path=/`. На HTTPS — префикс `__Host-`.
- Срок жизни 30 дней со скользящим продлением; «Выйти» удаляет сессию в базе и cookie.
- JWT не используем: серверную сессию можно мгновенно отозвать.

## Разграничение доступа

- Каждая страница и каждое действие получает пользователя через серверный слой доступа к данным (`server-only`), который проверяет сессию. Без сессии — редирект на `/login`.
- **Все запросы к данным фильтруются по `userId` из сессии**, а не по id из адреса или формы. Чужая заявка по прямому адресу возвращает 404 (не 403 — не раскрываем сам факт существования).
- Роли: `student`, `teacher`, `staff`. Доступ к кабинетам сотрудников проверяется на сервере.
- Server Actions Next.js проверяют Origin (защита от CSRF) — дополнительно к `SameSite=Lax`.

## Секреты

- Все секреты (`AUTH_PEPPER`, будущий ключ ИИ) — только в `.env` на сервере, который не попадает в git. В репозитории — `.env.example` без значений.
- На клиент не уходит ни один секрет; ИИ-ассистент будет вызываться только с сервера.

## Заголовки безопасности

`X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Permissions-Policy` с отключёнными камерой/микрофоном/геолокацией.

## Данные

- Только вымышленные персонажи. Демо-пароль у всех тестовых аккаунтов один и публичный (`orbita-demo`) — это осознанно для жюри; хранится он, как и любой пароль, только в виде хеша.
- База: SQLite через Prisma на этапе прототипа (на сервере нет PostgreSQL). Схема переносится на PostgreSQL сменой провайдера.

- Запись на консультацию: проверка лимита мест в транзакции (подсчёт → вставка → повторный подсчёт). В SQLite записи сериализуются; при переезде на PostgreSQL — уровень изоляции Serializable или блокировка строки консультации (`SELECT … FOR UPDATE`).
